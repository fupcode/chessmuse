# ChessMuse（棋妙）项目总纲

> 版本：v0.4（MVP：核心讲解质量优先）  
> 项目目录：`chessmuse`  
> 文档位置：`docs/overview.md`  
> 当前目标：构建一个能动态演示、且讲解内容有实质分析价值的中国象棋 AI 复盘 MVP。开发按依赖关系与验收条件推进，而非按固定天数划分。


## 1. 项目定位

ChessMuse 是一个**会讲棋、会动棋，并能对比普通直觉与专家判断的 AI 中国象棋复盘解说员**。

输入一局棋谱后，系统应当：

1. 使用 Pikafish 分析实际走法、候选走法和后续变化。
2. 使用传统手工评价与有限深度搜索构建一个可解释的“直觉模型”，近似模拟短视、贪子或容易忽略深层战术的思考。
3. 对比直觉模型与专家引擎，寻找值得讲解的认知落差。
4. 识别关键失误、明显战术机会，以及 MVP 范围内的弃子攻杀/弃子争先候选。
5. 将搜索证据组织成局面、候选走法、关键变化和战术事件，交给 LLM 生成讲解。
6. 通过棋盘动画、TTS 和滚动字幕，将讲解呈现为一段完整复盘。

目标不是宣称浅层搜索就等于真实人类思维，而是构建一个**可解释、可替换、可用棋谱样本验证的有限理性近似模型**。

## 2. MVP 范围与优先级

### P0-A：基础展示骨架（先完成，控制投入）

- 内置至少一局经过人工检查的中国象棋棋谱；不以多格式上传为前提。
- 棋盘能按合法走法自动回放实战主线。
- 可以在关键局面切换到一条推演变化，再返回实战主线。
- 提供播放/暂停/重播，以及最基本的关键节点跳转。
- 棋盘旁显示解说字幕，TTS 播放一条稳定的中文声音；按段落同步即可。
- 先用手写脚本验证播放器，再接入动态生成内容。

**验收：** 不依赖在线 LLM，也能播放一段带棋盘走子、推演、语音和字幕的示例。基础骨架完成后，立即转向分析内核，不继续沉迷于 UI 装饰。

### P0-B：分析内核与讲解质量（本次主要投入）

#### 1. Pikafish 专家分析

- 分析实战每步或关键局面的评价变化。
- 对筛选出的局面获取最佳走法、少量有意义的候选走法及主要变化。
- 能对指定直觉候选单独搜索，避免只看 MultiPV 前三名而漏掉明显诱人但很差的走法。
- 采用“全局低成本扫描 + 关键局面深度复查”，控制计算量。

#### 2. 有限理性/人类直觉模型原型

这是 ChessMuse 的差异化内核之一，不能直接推迟到未来版本。

- 优先调研并尝试改造 ElephantEye 等传统中国象棋引擎，复用合法走法生成和传统搜索框架。
- 构建至少两种可比较的手工评价配置，例如：
  - 纯子力与直接吃子收益；
  - 子力 + 位置表 + 基本将帅安全/受攻击特征。
- 对多个浅层深度进行实验，例如静态/1 ply、3 ply、5 ply；深度应作为实验变量，而非直接当成人类棋力等级。
- 输出各配置的候选走法、排序、评分和必要的变化。
- 与 Pikafish 对比，找出“直觉上吸引人但客观很差”以及“浅层不易发现但专家认为优秀”的走法。

若 ElephantEye 的构建或改造遇到严重阻塞，应先限时排查；应明确阻塞条件与切换后备方案的标准。记录阻塞原因，并使用可运行的简化手工评价 + 合法走法搜索作为明确的临时后备方案。无论采用哪条路径，MVP 都必须产出一个能实际运行并与 Pikafish 比较的直觉模型，而不只是写调研报告。

#### 3. 关键节点与妙手候选识别

MVP 不追求完美识别所有妙手，但必须超越“只按评分波动挑节点”。至少覆盖以下几类：

- **明显失误/漏算战术：** 实际走法相对最佳走法的评价损失较大。
- **认知落差：** 直觉模型偏好的走法被专家模型显著否定，或专家最佳走法在浅层模型中排名很低。
- **弃子攻杀候选：** 物质牺牲后出现强制将军、杀棋威胁或连续战术。
- **弃子争先候选：** 暂时损失物质，但深搜仍认可，且后续存在持续有效威胁或对手应法受限。

关键节点选择应结合评价波动、候选差距、认知落差和战术事件。每局最终挑选少量高价值节点讲清楚，不要求自动标注每一步。

#### 4. 弃子争先的可解释启发式

先做可验证的 MVP 级启发式，不要求先完成经过充分校准的复杂评分公式。

需要分别记录：

- **牺牲量：** 物质变化、是否短期收回、是否构成净牺牲。
- **专家认可度：** 弃子走法与最佳走法的评价差距，以及提高搜索深度后评价是否稳定。
- **主动权证据：** 有效将军、捉子、杀棋威胁、强制应对、对手合理应法数量等。
- **分支稳健性：** 对手接受或拒绝弃子时的代表性变化与评价。
- **认知反差：** 直觉模型是否因眼前物质损失而排斥该走法。

不要仅凭“弃了高价值棋子”“对手合法走法少”或“PV 里连续将军”就判定妙手。输出应称为“弃子争先候选/证据”，并让深度搜索和变化分支支撑结论。

#### 5. 证据驱动的 LLM 解说

LLM 不直接看一堆原始棋步后自由发挥。程序先生成结构化事实包，至少包含：

- 当前局面与实际走法。
- 直觉模型候选及其理由/评价特征。
- Pikafish 最佳走法、实际走法损失和候选对比。
- 关键变化、分支评价和事件位置。
- 已验证的吃子、将军、物质变化、强制威胁等事件。
- 该节点被选中的原因及证据强度。

讲解直接围绕棋局中的诱惑、风险、走法和后果展开，用自然口语衔接，例如“这里可不能光顾着吃马”，随后用具体变化解释。直觉与专家对照只作为后台选材与核验依据，不向观众播报“先看直觉”“两套模型的分歧”等内部流程；不固定复述同一套段落标题。表达可以生动，但不能编造走法、战术或引擎结论。

### P1：核心闭环通过验收后再做

- 上传棋谱文件；优先只支持一种格式，不为多格式兼容投入过多时间。
- 评估曲线与每步评分的完整可视化。
- 更多候选分支和复杂分支浏览。
- 多种解说风格、多个 TTS 声音。
- 基于 TTS 时间戳的逐句/逐字字幕同步。
- 观众针对任意一步追问并实时追加推演。
- 更精细的自动节点排序与更丰富的妙手类型覆盖。

### 本次明确不要求

- 完整覆盖所有象棋妙手类别。
- 完整、准确地模拟所有真实人类棋手的认知过程。
- 大规模人类棋谱拟合、严格的跨棋力等级预测实验。
- 长篇论文综述或大规模基准评测。
- 训练专用 LLM、复杂 Agent 框架、实时对弈平台、用户体系、支付和视频导出。

这不意味着可以跳过核心算法调研：必须做**直接服务于当前实现的定向调研、小样本局面实验和人工核验**，只是暂不追求学术研究规模。

## 3. MVP 的目标演示

准备两类示例，至少确保其中一类可以稳定完整播放：

1. **高手棋局：** 展示一处直觉不容易发现、但专家搜索支持的妙手；如果有合适案例，优先选择弃子攻杀或弃子争先。
2. **普通/示例复盘局：** 展示一处看似合理、但专家引擎明确否定的走法，并对比更好的替代方案。

理想的讲解顺序：

1. 展示局面和实战走法。
2. 解释普通棋手可能首先注意到什么。
3. 用具体走法说明眼前的诱惑或容易忽略的风险。
4. 顺着攻防需要，引出经过核验的关键走法。
5. 播放关键变化，验证战术后果。
6. 总结这一步的棋理和可迁移的经验。

不要为了讲解长度而逐步点评整盘棋。宁可讲透 2～4 个关键节点，也不要生成十几段泛泛而谈的评论。

## 4. 核心数据流

```text
内置棋谱 / 单一格式棋谱
        ↓
棋谱解析、合法性验证、局面快照
        ↓
Pikafish 专家分析 ─────────────┐
        ↓                      │
有限理性模型：手工评价 + 浅层搜索 │
        ↓                      │
候选排序与认知落差比较 ←─────────┘
        ↓
关键节点筛选与妙手类型候选
        ↓
关键分支定向搜索、事件提取
        ↓
结构化解释证据包
        ↓
LLM 生成讲解脚本
        ↓
TTS 分段音频 + 字幕
        ↓
统一播放调度器：棋盘 + 语音 + 字幕
```

## 5. 播放与展示：够用即可

### 5.1 统一播放调度器

所有走子、讲解、分支切换都进入同一条事件时间线。最少支持：

- `move`：执行已验证的走法。
- `speak`：播放音频并高亮对应段落字幕。
- `set_position`：跳转到已验证的局面快照。
- `highlight`：可选，突出棋子/格子/箭头。

音频播放完成后再推进依赖该讲解的后续事件。暂停、重播和跳转必须同时更新棋盘、字幕与音频状态。

### 5.2 字幕同步

MVP 只需**段落级同步**：当前讲解段高亮、自动滚动。逐句或逐字精确时间戳不是当前重点。

### 5.3 语音

只接入一个稳定的中文 TTS 声音。优先提前生成并缓存音频，保证演示可靠；多声音和复杂情绪控制推迟。

### 5.4 棋谱输入

优先使用经过人工检查的内置棋谱。如果上传功能几乎没有集成成本，可以支持一种格式；多格式兼容、复杂错误提示和图片识别均不阻塞核心算法工作。

## 6. 实施步骤与阶段验收

### 步骤 1：建立最小展示闭环

**任务：**

- 实现棋盘显示、主线走子、暂停、继续与重播。
- 能从关键局面切换到一条预定义推演分支，并正确返回主线。
- 接入单一中文 TTS，旁侧显示对应讲解段落并自动滚动。
- 用人工编写的合法棋步与讲解脚本验证播放事件协议，不依赖 LLM 或引擎分析。

**交付：** 最小可运行 Web 演示、示例脚本、基础播放协议。

**验收门槛：** 一段包含实战走子、分支推演、语音与字幕的示例可以完整播放；暂停、重播与回到主线不破坏棋盘状态。通过后停止非必要的界面美化，转入分析核心。

### 步骤 2：建立棋局与专家分析基础

**任务：**

- 接入棋谱解析、合法性检查和局面快照。
- 接通 Pikafish，输出评分、主要变化与候选走法。
- 对实际走法以及指定候选能够进行可复现的分析。
- 建立全局扫描、关键局面复查与分析结果缓存的基本流程。
- 收集覆盖失误、战术、反直觉妙手及弃子的代表性测试局面。

**交付：** 专家引擎适配器、分析结果结构、基础测试局面集。

**验收门槛：** 对一局合法棋谱可重复得到可验证的局面与搜索证据；能够针对某个指定走法分析而非仅依赖 MultiPV 前几名。

### 步骤 3：实现并验证有限理性模型

**任务：**

- 定向调研 ElephantEye 等传统引擎的手工评价、搜索接口、构建方式与许可证。
- 选定可运行实现：优先复用传统引擎；若有明确技术阻塞，则采用可维护的手工评价 + 浅层搜索后备方案。
- 提供至少两种评价函数配置，以及多种搜索深度的候选输出。
- 明确区分“不同搜索深度的首选”与“同一深度下的候选排名”。
- 与 Pikafish 对照，记录直觉偏好与专家判断的差异，检视典型误判案例。

**交付：** 可执行的有限理性模型、候选对比结果和小样本实验记录。

**验收门槛：** 给定代表性局面，能够稳定输出各配置下的候选、排序及评价依据，并与专家搜索进行真实对比；不得只以调研报告替代实现。

### 步骤 4：关键时刻、妙手候选与解释证据

**任务：**

- 综合评分损失、局势转折、认知落差与战术事件筛选关键节点。
- 实现失误、弃子攻杀、弃子争先等核心类型的候选检测。
- 对弃子分别检查物质牺牲、专家认可度、持续威胁及关键应法；证据不足时不强行归类。
- 为关键候选构建局部变化树，标注可验证的将军、吃子、得失子及评价变化。
- 将主线、分支、事件与分析理由整合为结构化证据包。

**交付：** 节点筛选器、基础妙手候选检测器、变化树及解释证据 Schema。

**验收门槛：** 在代表性局面中，能说明某节点为何入选，并给出支撑失误或妙手判断的合法变化与事件证据；反例不能被无条件评为妙手。

### 步骤 5：生成高质量讲解并接入播放

**任务：**

- 根据证据包生成自然的分段讲解，把走法的吸引力、风险和后果讲清楚，避免播报内部模型与分析阶段。
- 将讲解、走棋和分支切换编译成统一播放事件；先校验棋步合法性，再交给前端。
- 生成并缓存 TTS 音频，提供段落级字幕同步。
- 对典型棋局人工检查解说中每个具体战术断言是否与变化证据一致。
- 准备覆盖高手赏析和普通复盘的稳定演示案例。

**交付：** 可端到端运行的 ChessMuse MVP、可复现的分析/解说缓存、运行说明及演示棋谱。

**验收门槛：** 能完整播放至少一局包含若干实质性关键节点的复盘，准确展示直觉与专家的分歧，并通过棋盘推演、TTS 和字幕解释其原因。

### 步骤 6：针对质量问题迭代

以真实演示结果为依据，优先修复以下问题：

1. 解说出现不成立的战术、错误引用或缺乏证据的断言。
2. 有限理性模型与专家模型无法产生有解释价值的对比。
3. 妙手检测误报、漏报，或关键变化缺失。
4. 棋盘、语音、字幕出现不同步或状态错误。
5. 在以上质量达到要求后，再改善外观、格式兼容、语音选择、评估曲线和实时追问。

**步骤之间可以进行独立模块的并行开发，但不得跳过各项验收门槛，也不要将调研报告数量或耗时视为进展指标。**

## 8. 评测与质量控制

### 8.1 小样本测试集

MVP 不以大规模评测为门槛，但必须准备一个人工检查的小型局面集，建议从 10～20 个代表性局面起步，覆盖：

- 直接吃子诱惑与简单反击。
- 明显失误与漏算战术。
- 反直觉最佳走法。
- 弃子攻杀。
- 弃子争先候选。
- 表面弃子但实际不成立的反例。
- 浅层搜索与深层搜索结论不同的局面。

### 8.2 必须记录的结果

- 每种直觉模型配置的首选与候选排序。
- Pikafish 对候选的评价与主要变化。
- 节点被选中作为讲解重点的原因。
- 弃子类型判断所依赖的证据。
- LLM 解说与证据是否一致。

### 8.3 质量原则

- 不把原始引擎分数差直接当作跨局面通用标准。
- 不把 PV 中出现连续将军直接当作主动权成立。
- 不把高物质牺牲或低候选数量单独当作妙手证据。
- 不声称有限理性模型已准确模拟真实人类；先称其为“直觉模型/有限理性模型”。
- 如果证据不足，应降低措辞强度或不生成该结论。

## 9. 针对性调研任务

调研只服务于实现决策，优先快速阅读代码和官方文档，不写长篇论文综述。

1. **ElephantEye：** 评价函数、搜索入口、编译方式、许可证、如何输出候选和控制深度。
2. **Pikafish：** UCCI/引擎通信、MultiPV、指定走法搜索、PV 和评价输出。
3. **棋谱/棋盘库：** 选择集成成本低、能保证合法走法与棋盘状态一致的棋规/棋盘方案，避免自行实现全部规则。
4. **妙手识别：** 只查与当前 MVP 直接相关的弃子、战术事件、候选评价方法。
5. **LLM 解说：** 研究如何把候选对比和变化证据组织为结构化提示，并验证事实一致性。

大规模人类棋谱认知拟合、完整学术综述和大规模基准测试放在 MVP 之后。Agent 必须把调研结论转化成运行实验或代码，不得用文档产出替代内核实现。

## 10. 给 Agent 的执行准则

1. 先通过最小棋盘、播放、字幕与单一 TTS 的验收门槛；随后优先投入分析内核。
2. 不要把“有限理性模型、认知落差、妙手候选”写成未来计划；MVP 必须有可运行的最小版本。
3. 优先评估并改造 ElephantEye；如构建、接口或许可证存在阻塞，明确记录原因并切换到手工评价 + 浅层搜索后备方案。
4. 用 Pikafish 评估直觉候选，并保留原始搜索证据。
5. 优先实现最能提升讲解质量的关键节点类型，不以覆盖全部妙手类别为验收要求。
6. 弃子争先先做可解释的多特征启发式，不宣称评分已严格校准。
7. 只把合法且已验证的变化交给播放器；LLM 不能直接控制任意棋步。
8. 不为多格式上传、多语音、逐字字幕、漂亮曲线和现场追问牺牲核心分析时间。
9. 用小样本局面逐个验证关键讲解；发现讲解不可靠时，优先修复证据和筛选规则，而不是继续润色文案。
10. 每个实施步骤都要提供可运行或可复现的交付物并通过明确验收；最终交付包含启动说明、演示棋谱、缓存分析/音频及可重复的演示流程。

---

**本项目 MVP 的成功标准：** 用户看到的不只是一个会动棋盘、会说话的界面，而是一段有真实分析内核支撑的复盘：系统能够展示普通直觉与专家判断的差异，用具体变化解释失误或妙手，再通过棋盘、TTS 和字幕把原因讲清楚。
