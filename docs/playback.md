# 第一阶段：播放闭环

本阶段只构建播放骨架。内置片段从标准开局开始：炮二平五、马8进7、马二进三、马2进3；分支尝试先跳左马，再恢复至第 4 半回合；主线继续起车、出马与进炮。它不是专家分析样本，不宣称任何一条变化更优。

## 播放协议 v2

源脚本为 `src/chessmuse/data/demo.json`，由 `compile_demo()` 逐步验证后通过 `/api/demo` 返回。

| 事件 | 源字段 | 执行含义 |
| --- | --- | --- |
| `move` | `move`：ICCS，如 `h2e2` | 验证走法，生成报步字幕与音频引用；音频开始时同时走子，等报步结束再推进 |
| `set_position` | `mainline_ply`，可选 `branch` | 恢复已验证的主线快照；有分支名时进入推演 |
| `speak` | `paragraph`，可选 `chapter` | 播放对应缓存音频并显示当前段落；音频完成后推进 |

所有事件都有唯一 `id`。编译器给每个事件附加完整 `state`，包含 `fen`、`ply`、`branch`、`caption` 与 `last_move`。走子事件另有 `before_state`、`paragraph`、`gives_check` 和 `animation_ms`。每步短句由 LLM 根据行棋方、合法中文棋谱、已核验事实和近期上下文压缩生成，保留行棋方且不含逗号等标点。结果提前缓存，播放不依赖在线 LLM；音频生成命令使用编译后的完整段落列表。ICCS 的 a0 在红方左下角，FEN 从黑方底线开始。前端只渲染通过校验的快照，主线上的每一步必须与独立棋谱吻合，时间线最后必须回到主线终点。

`Player` 统一持有音频对象、定时器和动画控制器。走子与报步属于同一个事件：声音实际开始播放后才启动动画，动画时长为 `min(550ms, 报步时长 × 60%)`，因此先完成落子，再听完报步。有详细解释时，在该 `move` 后安排 `speak`；没有则直接安排下一个 `move`。`set_position` 即时切换，不额外等待。语音关闭时仍按对应音频时长保留字幕。

暂停同时保留音频位置、动画进度或剩余定时；音频缓冲时也暂停动画，恢复发声后继续。跳转会清理旧音频、动画和定时器，停在所选走子的起始局面，点击播放后重新报步并走棋。重播从头开始；「回到主线」跳至恢复后的讲解事件。切换声音开关会重新开始当前事件。减少动态效果模式下直接落子。动画使用可暂停、继续和取消的 Web Animations API。

## 验证记录与边界

已在本机完成合法主线与分支校验、音频生成和音频时长读取、HTTP 页面/数据/音频访问，以及棋规和播放器状态测试。音频清单保存合成时的原文、声音名称和文件名，校验原文一致性，不计算文件哈希。

默认缓存为晓晓神经网络女声（`zh-CN-XiaoxiaoNeural`，语速 `+20%`，即 120%）的 MP3，通过 edge-tts 联网生成，播放无需联网。仍兼容 Windows 慧慧的 WAV 缓存。所有段落生成并校验成功后才更新当前清单，失败不切换声音。每次生成使用独立文件名，避免浏览器缓存旧音频；运行中的服务仍使用启动时清单，因此更换声音后需要重启服务。

本次开发会话未提供可用浏览器，尚未完成真实浏览器画面检查、听音和完整交互验收。因此第一阶段保留以下人工验收，不据自动化测试宣称整个 MVP 或阶段验收已经完成。

## 浏览器验收步骤

1. 启动服务，打开首页。应显示标准初始棋盘，红方在下，共 32 子。
2. 点击播放：先听到中文引言；每步短报步与对应棋子移动同时开始，落子在报步结束前完成。部分走子之后有详细解释，其余直接接下一步。
3. 在棋子移动途中暂停，等几秒后继续：声音与棋子都应冻结，再从各自暂停位置继续。字幕不跳到后续事件。
4. 点击「推演变化」，再播放：应从第 4 半回合开始先跳红左马，再起黑右车。
5. 推演中点击「回到主线」：两步分支走子被撤回，棋盘恢复第 4 半回合并保持暂停；继续播放后先起红左车。
6. 拖动进度到其他事件、点击「重播」：旧声音应停止，棋盘和字幕同时定位。
7. 关闭中文语音完整播放一遍，再开启声音播放一遍：最终主线应到第 8 半回合，显示片段总结，没有并发走子或漏段。
8. 缩小浏览器至手机宽度，棋盘和按钮应完整可见，讲解位于棋盘下方。

验收通过后进入总纲步骤 2；下一阶段的首要交付是专家引擎的指定候选搜索和原始分析记录，随后建立直觉模型的真实对照。
